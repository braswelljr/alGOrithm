# Generated lists come from the registry

Every list of entries in the documentation is generated from the registry by `tools/gendocs`: the catalog section of `README.md`, between its `catalog:begin` and `catalog:end` markers, and the whole of `docs/catalog.md`. Nobody edits them by hand, and a test fails when they are stale.

## Why

The registry is the one list of what can be run ([there is one list of entries](there-is-one-list-of-entries.md)). A second, hand-written list in the README drifts the first time someone adds an entry and forgets it: the old README linked to a file that was never written, gave jump search the wrong complexity and left out eight packages. Generating the lists is the DRY answer ([design principles](design-principles.md)): the name, cost, Go function and example command of an entry are written once, in the registry, and appear everywhere from there.

## What it looks like

```bash
go run ./tools/gendocs          # write README.md's catalog and docs/catalog.md
go run ./tools/gendocs -check   # report what is out of date, exit 1
```

`README.md` holds only the markers; the generator writes between them:

```markdown
<!-- catalog:begin (generated by `go run ./tools/gendocs`; do not edit) -->
...
<!-- catalog:end -->
```

Do: change a name, summary or cost in `internal/core/*.go`, then run the generator.

Do not: edit between the markers or in `docs/catalog.md`; the next run overwrites it and the test fails until then.

## How it is checked

`TestGeneratedDocsAreCurrent` in [`tools/gendocs/main_test.go`](../../tools/gendocs/main_test.go) regenerates both files in memory and fails if either differs from what is committed. It runs in `go test ./...`, so in `make ci` and the Tests workflow.
